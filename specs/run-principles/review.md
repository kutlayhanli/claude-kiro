## Refuted
| ID | Problem | Why it was refuted |

| R5 | 15.2's "with that task on the base" is ambiguous: `base` also names the main branch in the land JSON, and the wording could allow a gate on a group that contains the task. | This is mainly rewording. The design already says the blaming gate is "a gate on exactly `merged`, on the current head", and that a RED task's failures come from the gate whose tasks are exactly that task. Bisection blames only at a single-task node, so the group reading is not a live risk. |
| R6 | Two behaviours that 14.5 relies on appear only in the design: the record is cleared on recovery, and a failed reset keeps the record. | The spec already handles both. `clear_refusal` removes the record only while it names that head. The error table maps a failed reset to 14.1, with the record kept. TC-167 and TC-196 assert both behaviours. Adding new criteria would only restate design detail. |
| D3 | The design gives `ck worktree merge` no way to receive or report a restore, and a text line would corrupt `--json` output. | This is an implementation detail and partly speculative. The design already says merge prints the restore line, and Task 95 owns both files. The only workflow caller of `ck worktree merge` runs it without `--json`. |
| D4 | A c+d interaction failure is never blamed on anyone, and 15.3's old trigger did not cover it. | The design's rule already reports it `unreproduced` ("when the batch gate was red and no task ended RED"). R4's rewrite of 15.3 now uses that trigger. |
| T4 | Task 98 checks `recovered` on the landing entry, but no fake option supplies it. | TC-169 (Task 100) already covers 14.2's workflow side end to end. The stray sentence in Task 98 is redundant. |
| T5 | Task 93 points to `protected_branch` in `tests/unattended_helpers.py`, which is the wrong file. | The task already says "or its equivalent", and the helper is an 8-line function that is easy to reproduce. |
| V5 | P-48 leaves a batch-only failure that comes with a culprit unspecified. | The design defines it: `unreproduced` only when no task ended RED. A leftover failure surfaces at the periodic or final full gate. D24 asks for no more. |
| V6 | No fake `recovered` option exists, TC-173 does not say how the target is made red, and "the periodic gate is not run twice" is untested. | TC-169 traces `recovered`. Making the target red in TC-173 is a test-setup detail. The untested rule is a nice-to-have, not a blocking defect. |
