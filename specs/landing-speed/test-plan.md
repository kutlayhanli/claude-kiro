# Test Plan: Landing Speed

**Created:** 2026-10-29
**Inputs:** [requirements.md](requirements.md), [PLAN.md](PLAN.md) (D1-D11 binding). Written without reading design.md, so these tests check whatever the implementation turns out to be.

## Strategy

This repo has three kinds of real boundary, and each criterion is tested at the one it crosses:

| Boundary | How tests reach it today | Used for |
|---|---|---|
| The Workflow script `plugin/workflows/spec-implement.js` | Node runs the **real script source** under the fake runtime in `tests/js/load_workflow.mjs`. Agents are stubbed by a fake project (`ck plan` semantics, landings, reviews). `tests/test_workflow_scripts.py` runs the Node suites from pytest. | Stories 1-3 (readiness, plan-agent schedule, task-owned worktrees, finish-first) |
| The `ck` CLI on a real git repo | `CliRunner` or `python -m claude_kiro.cli` subprocesses on temp git repos (`tests/conftest.py::project`, `tests/test_worktree_cli.py::repo`) running real `git` and real `pytest`. | `ck plan` (readiness contract), `ck worktree create/claim` (the commands the task prompt names), `ck gate` (xdist cap), `ck doctor` / `ck init`, `ck agents set` |
| `ck stats` over a Claude home | `tests/stats_helpers.py::FakeClaudeHome` writes real run files and transcripts. `ck` runs as a subprocess (`stats()`, `ck_sub()`), and records go to the isolated `XDG_DATA_HOME`. | Story 4 |

**How integration-first applies here:**

- No test mocks a `claude_kiro` module, git or the filesystem. A test reaches ck only through the CLI or through a named public decision seam (see Harness Contract). The only fakes are for things this repo does not own:
  - the Claude Code Workflow runtime and its LLM agents (the fake runtime and fake project);
  - Claude Code's on-disk run files (FakeClaudeHome);
  - the CPU core count (only inside seam-level properties).
- Workflow tests check behaviour that can be seen from outside the script: which agents are requested, in what order, with which prompts, against the fake runtime's own queue trace, plus the script's returned result and log. They never read the script's internal variables. The single exception is the readiness seam `readyTasks`, which NFR-2 requires as a contract against `ck plan`.
- When a prompt tells an agent to run a command (the task agent creating its own worktree), the test takes the command from the prompt the real script produced and runs it through the real `ck` CLI on a real git repo. This shows that the instructions actually work. Checking only that a string appears in the prompt would not.
- Unit-level tests cover only the pure decision seams: readiness, queue wait, wait split, worker cap, xdist hint, and setting coercion. Every one of them is property-tested with Hypothesis, and each seam also has one integration case showing that the CLI or script really uses it.
- **Property library:** Hypothesis, the only one the repo has (`dev` group). The repo has no npm dependencies and no fast-check, so the scheduler properties are generated in Python and run by the real script through a Node JSON-lines bridge (`tests/js/bridge.mjs`), not by a JS property library. Settings are deterministic: `@settings(derandomize=True, max_examples=200, database=None, deadline=None)` for pure seams and the readiness contract. Bridge-driven scheduler properties use `max_examples=60`, because each example runs the whole workflow, and the same derandomized, database-free settings.
- **Before the feature exists, each test fails for the right reason:**
  - The script has no `readyTasks`, no `deps` arg and no finish-first deferral.
  - Run files' `queuedAt` is not collected.
  - `ck gate` does not set `PYTEST_XDIST_AUTO_NUM_WORKERS`.
  - `ck doctor` and `ck init` print no xdist hint.
  - `ck agents set run.finish_first` is an unknown setting.
  - pyproject has no `pytest-xdist`.

## Test Infrastructure

### Exists (reuse as is)

- `tests/js/load_workflow.mjs`: `runWorkflow(scriptPath, { agent, args })` evaluates the real script source with stubbed `agent/parallel/pipeline/phase/log` and records the label corpus.
- `tests/js/spec_implement.test.mjs`: `project({...})` fake project (`ck plan` semantics over `deps/done`; `relink`; `busy`; `cycles`; `verifyCycles`; `checkRed`; `reviews`; `reviewDurations`; `mergeDurations`; `durations`; `conflicts`; and so on). It also has the `test(name, fn)` runner that prints `ok`/`FAIL`.
- `tests/test_workflow_scripts.py`: runs each `tests/js/*.test.mjs` in Node and fails on `FAIL` or a non-zero exit. It skips when `node` is missing.

  - `project` fixture: a real git repo with `calc.py`, `tests/`, `specs/calc` and `specs/ck.json`;

- `tests/test_stats_show.py::show_json`, and the `env` fixture pattern in the stats tests.
- `tests/test_plugin.py::test_dogfood_copies_in_this_repo_match_the_plugin_source` covers NFR-3, the vendored copy being byte-identical.

### To add

1. **`tests/js/fake_project.mjs`** (moved out of `spec_implement.test.mjs` without changing behaviour, so the new suite and the bridge share it). It also gains:
   - `plan` answers carry `deps` (the current dependency map, after any `relink`) and `remaining`. (1.9 is about args without dependency information, not about plan answers without it, so there is no old-shape plan answer option.)
   - `planDurations: { k: ms }`: plan call k takes that long, so tasks can start and finish while it runs (TC-62).
   - `externalDone: { atPlan: k, tasks: [...] }`: from plan call k on, those tasks are Done on the target although the run never started them (committed directly).
   - `planFail: [k, ...]`: plan call k and its retry both return `{ error: 'boom' }` with empty arrays.
   - `worktree: { <n>: { state: 'BUSY'|'ERROR'|'EXISTS'|'CREATED', detail } }`: the first task agent of task n returns that worktree outcome. BUSY and ERROR come with `status: 'blocked'`, `gatePassed: false` and `commits: ''`. Default is `CREATED`.
   - The plan agent no longer filters `ready` through a worktree step. It answers with `ck plan` data only, because the plan agent no longer creates worktrees (2.1).
2. **`tests/js/load_workflow.mjs`** extensions (existing callers unchanged):
   - `runWorkflow(scriptPath, { agent, args, slots })`: if `slots` is a positive integer, at most `slots` agent calls run at once and the rest wait in FIFO order, as the real runtime queue does (documented cap min(16, CPUs − 2), observed 14; FIFO start order is an assumption, requirements Assumptions). The returned object gains `trace`: `[{ t, ev: 'request'|'start'|'end', label }]`, where `t` comes from `performance.now()`. Without `slots`, nothing ever queues.
   - The real runtime gives the script no start signal (requirements, Assumptions). The script presumes agents queued from `args.agentSlots` (design, "Queued: the observable approximation"), so every case or scenario with `slots` also passes `args.agentSlots = slots`; without `agentSlots` finish-first is inert (TC-63). Tests only assert on `trace`, never on the script's estimate itself.
   - `loadFunction(scriptPath, name)`: extracts a top-level `function <name>(...) {...}` declaration from the script source by brace matching and evaluates it alone. It throws if the function is missing or refers to script state.
3. **`tests/js/bridge.mjs`**: a long-lived Node process that reads JSON lines on stdin and writes one JSON line per request:
   - `{op:'ready', deps, done, exclude}` returns `{ready}` through `loadFunction(SCRIPT,'readyTasks')`.
   - `{op:'run', project:{...fake_project options}, args:{...}, slots}` returns `{result, logs, trace, prompts, events}`.

   Wall time is scaled down: all durations are milliseconds, 1-40.
4. **`tests/js/landing_speed.test.mjs`** (Stories 1-2) and **`tests/js/finish_first.test.mjs`** (Story 3: TC-23 to TC-29, TC-63): the Node example suites. Both are added to the `test_workflow_scripts.py` parametrize list.
5. **`tests/landing_bridge.py`** (helper module): a module-scoped pytest fixture `bridge` that starts `node tests/js/bridge.mjs` once and exposes `bridge.ready(deps, done, exclude)` and `bridge.run(project, args, slots=None)`. It skips if `node` is missing. It also holds Hypothesis strategies:
   - `dags()`: 1-25 tasks, ids drawn from `1..120`, non-contiguous and multi-digit (for example `{1, 2, 9, 10, 11, 100}`), edges only from higher to lower index, so the graph is acyclic;
   - `subsets(ids)`;
   - `scenarios()`: DAG, durations, `reviewDurations`, `mergeDurations`, review verdict sequences that force revisions, `checkRed`, `maxConcurrent` in {1..4, null}, `mergeBatch` in 1..4, `slots` in {1..6, null}.
6. **tasks.md writer for the readiness contract:** `write_spec(dir, deps, done)` uses `tests/test_waves.py::task()`-shaped blocks:
   - impl track only, no `Verifies`, so no verify-order cycles;
   - `**Status:** Done` for Done tasks;
   - `**Dependencies:** Task a, Task b`;
   - dangling deps written as references to task numbers that are not in the file;
   - no `## Parallel Groups` section.

   It runs `ck plan demo --json --exclude ...` through CliRunner in a `tempfile.TemporaryDirectory()` git repo, created per example rather than with `tmp_path`, because of Hypothesis's function-scoped-fixture health check.
7. **`tests/stats_helpers.py`:**
   - `AgentSpec` gains `queued_at_ms: Optional[int] = None`, written as `queuedAt` when not None, and `omit_started: bool = False` (no `startedAt` key), plus `raw_progress: Optional[dict]`, merged over the generated `workflow_agent` entry to inject odd values (strings, bools, null).
   - `TaskSpec` already carries `finishedAt` and `mergedAt` through `implement_result`.
   - These are additive; existing defaults are unchanged.
8. **`tests/fixtures/stats/pre-queue-record.json`:** a stats record produced by today's collector (before this change) from a FakeClaudeHome run. It is generated once by the test task with the current `ck stats collect` and committed. 4.7 reads it without re-collecting.
9. **`tests/conftest.py` autouse additions** (needed because the suite itself will run under xdist inside a `ck gate`):
   - `monkeypatch.delenv("PYTEST_XDIST_AUTO_NUM_WORKERS", raising=False)`. Otherwise the outer gate's value is inherited and every inner-gate test sees the pass-through case (6.2).
   - `monkeypatch.setenv("CK_GATE_RUNDIR", str(tmp_path_factory.mktemp("gates")))`, so parallel test workers' real gates never count each other.
10. **Gate probe project** (fixture `gate_probe` in `tests/test_gate_xdist.py`): the `project` fixture plus `probe.py`, a verify command `python probe.py <tag>` that:
    - writes `os.environ.get("PYTEST_XDIST_AUTO_NUM_WORKERS")` and `sys.argv` to `<tag>.json` in a shared temp dir;
    - with `HOLD=<file>` in its argv, touches `<tag>.started` and then waits (polling, at most 60 s) until `<file>` exists.

    Helpers:
    - `start_gate(project, tag, hold)` returns a `Popen` of `python -m claude_kiro.cli gate calc` in its own process group;
    - `wait_started(tag)`;
    - `release(hold)`;
    - a second `project` copy (`project_b`) for the cross-project case.
11. **Doctor/init helpers** (`tests/test_doctor_xdist.py`): an `inited` fixture runs `ck init --no-allow-workflow` in a temp git repo with `pyproject.toml`. Then `set_verify(project, [...])` rewrites `specs/ck.json`, `doctor(project)` returns `(exit_code, warnings_bullets, issues_bullets)` using the `_bullets` parser from `tests/test_stats_doctor.py`, and `stable_suite` / `pid_suite` are tiny pytest projects (one with a `@pytest.mark.parametrize("p", [os.getpid()])` test) for running the hint's one-line check.

## Harness Contract

These are the names the tests rely on. If the design renames one, the test tasks follow the design, and the review must check that every row above still maps to it.

1. **Workflow args (1.1, 3.5, 3.6):**
   - `args.deps: { [task: string]: string[] }`, copied from `ck plan --json` `deps`.
   - `args.agents.run.finish_first: boolean`. Absent or `true` means on; `false` means off.
   - When `args.deps` is absent, the 1.9 fallback applies.
2. **Readiness seam (1.2, NFR-2):** `plugin/workflows/spec-implement.js` declares a top-level `function readyTasks(deps, done, exclude)`.
   - Arguments: a deps map, an array of Done task ids, an array of excluded ids.
   - It returns a new array of task-id strings in launch order.
   - It must be self-contained (it uses only its parameters, its own nested helpers and JS built-ins), so `loadFunction` can evaluate it alone.
   - The script's own scheduling must call it. TC-55 checks this.
3. **Plan agent answer (1.6):** the `PLAN` schema gains `deps` (same shape as 1). The fields `done`, `ready`, `busy`, `remaining`, `cycles` and `verifyCycles` stay. `ready` is `ck plan`'s ready list, with no worktree filtering. `busy` may be empty.
4. **Queue observation (3.1-3.7):** the real Workflow runtime gives the script no signal when a requested agent starts, so the design presumes agents queued from `args.agentSlots` ("Queued: the observable approximation"). The fake runtime (`slots` option) models a FIFO queue, and every case with `slots` passes `args.agentSlots = slots`. The tests assert only on the fake runtime's own `trace` (`request`, `start`, `end` per label), so TC-23/24/27/29 and P-8/P-11 judge by the runtime's real queue, not by the script's estimate.
5. **Task agent result (2.2-2.4):** the task agent's `RESULT` gains `worktree: { state: 'CREATED'|'EXISTS'|'BUSY'|'ERROR', detail?: string }`. BUSY gives the reason `worktree busy: ${detail}`. ERROR gives a reason containing `detail`. The first task prompt contains, on its own line, `ck -C <root> worktree create <spec> <n> --install --base <into> --json`, followed by a claim, `ck -C <worktreeDir>/<spec>-task-<n> worktree claim <spec> <n>`.
6. **Labels:** unchanged. They are `plan k` / `plan k retry`, `task N`, `task N retry k`, `task N revise k`, `review N`, `review N round k`, `land …`, `full gate @k`, `fix k (…)`, `re-check k`, `final gate` and `report`. No new label is a worktree-creation step.
7. **Deferral log (3.7):** each deferral period logs one line containing `finish-first`.
8. **Setting (3.6, 3.8):** `ck agents set run.finish_first <v>` with `--project` or global scope. `ck agents --json` exposes `roles.run.finish_first`, default `true`. The coercion is the same as for other booleans (`claude_kiro.agents._coerce('run', 'finish_first', v)` is the seam P-12 calls; the error message contains `true or false`).
9. **Stats (4.x):**
   - Stored agent rows gain `queueMs: int | null`.
   - `ck stats show <run> --json` gains:
     - `queueWaitMs`: `{ [kind]: { count, median, p90, total } } | null` (ms, null = not recorded);
     - `mergeWaitSplitMs`: `{ review: { median, total }, landing: { median, total } } | null`.
   - The text view has a queue-wait section headed `queue wait`, which reads `not recorded` when there is no data, and a review/landing split line beside `idle before merge`.
   - Seams:
     - `claude_kiro.analytics.collect.queue_wait_ms(entry: Mapping) -> Optional[int]`;
     - `claude_kiro.analytics.collect.merge_wait_split(finished_ms: Optional[int], merged_ms: Optional[int], intervals: Sequence[Tuple[int, int]]) -> Tuple[Optional[int], Optional[int]]` returns `(review_ms, landing_ms)`;
     - `claude_kiro.analytics.show.queue_summary(waits: Iterable[Optional[int]]) -> Dict[str, Optional[int]]` returns keys `count`, `median`, `p90`, `total`, with p90 by nearest rank.
10. **Gate (6.x):**
    - `claude_kiro.gate.xdist_env(environ: Mapping[str, str], cores: int, gates_running: Optional[int]) -> Dict[str, str]`: the full env passed to verify commands.
    - `claude_kiro.gate.machine_cores() -> int`.
    - The running-gates registry lives under `$CK_GATE_RUNDIR` when that is set; the default is one fixed per-user directory that does not depend on `TMPDIR`, shared by sandboxed and unsandboxed gates (requirements, Assumptions; design `registry_dir`). If it is unreadable, or is not a directory, the count is 1 and the gate is not failed.
    - The registry entry must vanish, or be ignored, once its process is gone.
11. **Doctor/init (7.x):** `claude_kiro.config.xdist_suggestion(verify: Sequence[str]) -> Optional[str]`. Doctor appends the string to `warnings`, and init prints the same string. It contains `pytest-xdist`, `-n auto`, the collection-mismatch pitfall and one backticked one-line check command.
12. **fake_project options:** `externalDone`, `planFail`, `planDurations` and `worktree` (Test Infrastructure 1). `runWorkflow` takes `slots` and returns `trace`. `loadFunction(scriptPath, name)`.
13. **Bridge protocol:** one JSON object per line, in `{op:'ready'|'run', …}` and out `{ok:true, …} | {ok:false, error}` (Test Infrastructure 3).

## Critical Paths

1. **Whole-spec run with script-side readiness:**
   1. The skill passes `deps` (TC-1).
   2. One start plan runs (TC-5).
   3. Ready tasks start from the script's own readiness (TC-2, TC-3, TC-4).
   4. Each task agent creates and claims its worktree (TC-14, TC-15).
   5. On finish, review starts at once (TC-26).
   6. Approved tasks land (TC-2).
   7. A plan runs after each landing and picks up Done and edits (TC-6, TC-8).
   8. Dependents start (TC-2).
   9. The final gate and git report follow (TC-8).
   10. Plan count stays bounded (TC-5, P-6).
2. **Finish-first under slot pressure:**
   1. A finish-type agent is queued by the runtime (TC-23); at saturation a finished task's review takes the next slot and no task start queues ahead of it (TC-65, P-23).
   2. New starts are deferred, and the deferral is logged once (TC-23, TC-29).
   3. Review, land, gate and fix agents are never held back (TC-26, P-9).
   4. When the queue drains, the deferred start happens at once (TC-24, P-11).
   5. Off, or with no queue, behaviour is as today (TC-25, TC-27, P-10).
3. **Worktree trouble at task start:** EXISTS is reused (TC-16, TC-17); BUSY is recorded and left alone (TC-18, TC-19, P-21); ERROR follows `onFailure` (TC-20); retries and revisions reuse the worktree (TC-21); the fixer still creates its own (TC-22).
4. **Measuring a run:**
   1. A run file with `queuedAt` is collected (TC-31, TC-32).
   2. `ck stats show` prints per-kind queue waits and the review/landing split (TC-33, TC-34).
   3. JSON agrees with the text (TC-36).
   4. Old runs and records still show (TC-35, TC-37).
5. **Parallel tests:**
   1. This repo's verify is `-n auto` with xdist declared (TC-38, TC-39).
   2. Test ids are stable (TC-40).
   3. Serial and parallel runs agree (TC-41).
   4. Concurrent gates share the cores (TC-42, TC-45, TC-46).
   5. A user-set value is respected (TC-43).
   6. Other projects get a hint, not a change (TC-49 to TC-53).

## Not Tested

- **The real Claude Code Workflow runtime and real LLM agents.** Neither can run in tests. The fake runtime stands in for the queue and the agents. Prompts are checked for content, and the commands they name are executed through the real CLI (TC-15/16/19). Whether a model actually follows the prompt is not tested.
- **The real runtime's agent cap and its queue order.** The cap is the documented min(16, CPUs − 2) (observed 14 on 16 cores) and FIFO start order is assumed (requirements Assumptions); neither can be observed in tests, and the fake models a FIFO queue. Finish-first properties hold for any cap from 1 to 6.
- **NFR-5 (the measured outcome on the next real run).** This is a manual check with `ck stats show` on the next whole-spec run of comparable size, per D5. `ck bench` is out of scope unless the results are unclear.
- **Real CPU oversubscription and wall-time effects of the worker cap.** The tests check the value handed to verify commands, not machine load. Running more gates than cores in one test is avoided; 6.3 is covered at the seam (TC-44, P-17).
- **PID reuse after a crashed gate.** A new process that gets a dead gate's pid could be miscounted until it exits. This is rare and cannot be produced reliably.
- **The tiered landing gate (option C), batch-fill delays, test-impact selection, a timer-based resync, a fixed slot reserve, a separate create-worktrees agent, and parallel flags for non-pytest runners.** All are out of scope (D1-D4, Out of Scope).
- **Unchanged safety logic** (landing lock, bisection, protected paths, sandbox, `ck worktree report`). Existing suites keep covering it: `tests/test_worktree_land.py`, `tests/test_worktree_report.py`, and `tests/js/spec_implement.test.mjs` (moved onto `fake_project.mjs` unchanged). No new tests are added, because this feature must not change them. The existing suites passing after the change is the check.
- **Retries under finish-first.** A `task N retry k` is a continuation, not a new task start. 3.1 does not govern it, and no test asserts either way.
