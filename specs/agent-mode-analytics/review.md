## Refuted

| ID | Problem | Why it was refuted |
|---|---|---|
| R7 | No criterion covers concurrent or overlapping collection of the same run. An implement run can last longer than 6 h. A `collect --all` (or a second terminal) then sweeps its open manifest as partial and closes it while the run is still going. The run's final `collect --agents --auto` then meets a closed manifest. Nothing says a closed manifest is still a valid source, that a later full collect clears `partial`, or that two collects racing on close_manifest/os.replace must not crash or duplicate the record. | Mostly handled already. read_manifest returns open, closed, missing or malformed (design.md:242), and the not-found path searches runs-closed, so a closed manifest is still a valid source. 3.9 already makes re-collecting a run `updated`. The concurrent-collect race is speculative and adds criteria beyond the lean scope. |
| R8 | Backfill takes the target branch from the session's git branch, which is the branch the main checkout was on. Agent-mode implement runs land on `--into <into>`, which can be a different integration branch. In that case the report succeeds against the wrong branch and gives a definite but false outcome (blocked or failed, nothing merged). 3.5's unknown-outcome rule only applies when the branch is missing or the report fails. | Backfill is an opt-in, labelled heuristic: records are partial and previewed with --dry-run (D8). The design already scopes the outcome to tasks with mergedAt at or after the group start (design.md:507, 622). The proposed fix would turn genuine all-failed or blocked runs into unknown, which makes the data worse to cover a rare wrong-branch case. |
| R10 | 1.2 says the target branch is "given, or else the current branch", but 1.1 and 1.4 define the command as only `--kind` and `--spec`, so the option that gives the branch is never named. The design adds `--into`, `--session` and `--override`, none of which a requirement covers. The instructions rely on `--into` to record the real landing target, so a requirements-only implementation could leave it out. | 1.2's 'given, or else the current branch' already implies a target-branch option. The design names --into, --session and --override precisely (design.md:126-137), and the tasks are built from the design. This is mostly a rewording. The suggested extra test for --override rejection adds scope beyond the decisions. |
| D5 | The design says create agents' `phase` is the spec-create phase title, but there is no mechanism that sets it. `_build_agent` takes `row["phase"]` only from `_Agent.phase` or meta `workflowPhase`, and Agent-tool metas have no `workflowPhase`. The matcher returns a `LabelMatch`, which has no phase field. `roles._create` returns role and step only. TC-30 (test-plan.md:141) asserts that role and phase match the workflow record. agentcollect builds the _Agent lists itself (design.md:117) and can set _Agent.phase, so this is an implementation detail TC-30 forces. No requirement asks for create-mode durations.phases or agentsConfig in agent mode, so that part is a nice-to-have. |
| D9 | In the spawn-worktree "Everything inherit, review off" path, agents are spawned as `general-purpose`. In the 'everything inherit, review off' path, the implementer and test_writer settings are both inherit, so the role split changes no model or cost attribution there.
